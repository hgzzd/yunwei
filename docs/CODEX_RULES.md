# Codex 实施规则

本文件是执行 M1–M4 时的强制边界。若用户的新指令与本文件或里程碑冲突，停止并请求明确的产品/架构决策；不得自行“优化”规则。

## 不可变约束

- 不更换技术栈，不引入替代桌面框架、游戏引擎、全屏覆盖层、云端服务或未确认产品能力。
- Rust 决定高层行为、权威位置、落脚点、Windows 环境和设置；TypeScript/Canvas 仅播放、插值、微动作、输入采样和气泡呈现。
- `pet` 与 `bubble` 永远是两个独立的小型透明窗口。不得以单个网页或透明全屏窗口替代。
- 每次工作只在一个里程碑内进行；可按模块分提交，但一个完成报告只能宣称已满足整个模块/里程碑的验收证据。
- 不修改不相关代码、依赖、资源或产品规则。遇到需要新规则的空白，记录问题并停下提问。

## TDD 工作循环

每个模块严格执行：

1. 先写针对该模块规则的失败测试；运行并保存“因功能缺失失败”的证据。
2. 写满足测试的最小实现，不提前实现下一模块。
3. 运行相关测试；重构后再运行相关测试和完整回归。
4. Windows API 功能先测试纯计算/策略和 trait mock，再做薄适配层；最后在原生 Windows 做手工验收。

不得以“难以测 Windows”跳过规则测试，也不得仅用手工点击替代单元/协议测试。

## 修改纪律

- 实施前读取对应 `docs/milestones/M*.md`、`docs/ARCHITECTURE.md` 和 `docs/TEST_STRATEGY.md`。
- 新 IPC 必须有 Rust 载荷类型、TypeScript 类型/解析、生产者测试、消费者测试和不兼容载荷测试。
- 新设置必须有默认值、版本迁移、归一化、损坏文件回退和安全恢复策略。
- 新 Windows 调用必须位于适配模块；避免在 `src-tauri/src/lib.rs` 添加业务策略分支。
- 保持现有 `npm run check`、Rust 测试和资源验证可运行；如命令自身需变更，先在对应里程碑文档中更新理由和验收。

## 提交与报告

提交顺序遵循里程碑文档，推荐“红测 → 最小实现 → 协议接线 → 适配层 → 验收/文档”。每次完成报告使用里程碑中定义的格式，必须区分：已自动验证、已 Windows 手工验证、未验证/受环境限制。禁止把计划、mock 通过或 WSL 结果描述成 Windows 成品验收。
